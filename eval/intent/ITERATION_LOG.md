# 意图识别快路径：方案与评测迭代记录

> 面试问答向的问题实录。对应代码：`src/core/agent/director/IntentClassifier.ts`、
> `DirectorAgent.ts`（chatFastPath 分发）、`PlanExecutor.ts`（executeDirectChatStream/Flow）、
> `prompts/intent_classify.md`（v3 定稿）；评测：`eval/intent/golden-set.json` + `run-eval.ts`，报告在 `eval/intent/reports/`。

## 1. 背景与问题

**现象**：在策划生成模式（design）发一条「你能做什么」，系统不直接回答，而是走任务规划 →
拆子任务 → 多智能体固定工作流，最后产出一份"策划案"。

**排查结论**：所谓"意图识别"在 design/table 模式**根本不存在**。系统里唯一的意图短路机制是
query 模式的 FAQ 快路径（向量匹配知识库 FAQ 命中即直答），但它依赖的 `kb_faq_match` 工具已随
Knowledge Hub 退役，`FAQ_ENABLED=false` 停用中。design 模式的链路是
`matchSkill（关键词匹配）→ TaskPlanner.plan → HITL → Router → 子 Agent`，其中 TaskPlanner 的
LLM 规划解析失败还会**降级成单任务继续跑**——任何输入都必然产出计划，没有出口。

**一个隐性教训**：原系统 `SkillManager.matchSkill` 就是关键词 `includes` 打分的"意图识别"
（命中"游戏/策划/设计"就走 default-design 工作流），这正是关键词分类法会误吞一切的真实案例。

## 2. 方案设计（决策与权衡）

**决策**：design/table 模式分发前加一道 LLM 意图分类，`chat` → 直接流式回复（不走规划/工作流）；
`task` → 完全走原流程。query 模式不动（其 agent prompt 已含闲聊直答指令）。

| 决策点 | 选择 | 理由与放弃项 |
|---|---|---|
| 分类器形态 | LLM 结构化输出（chat/task 二分类） | 规则/关键词无法覆盖中文语义边界（v1 错例全是规则法挡不住的）；嵌入相似度/微调小模型需要标注数据与部署成本，当前 77 例量级远不划算，留作规模化后的路径 |
| 失败方向 | **fail-safe：超时/解析失败/异常/超长输入一律判 task** | 两类错误的代价不对称：漏判（chat→task）只是多走一次流程；误吞（task→chat）会吃掉用户的真实任务。分类器只能放行"明显是闲聊"的消息 |
| 容错三层 | prompt 规则（拿不准判 task）→ schema 层宽容解析（非 `"chat"` 一律 task）→ 3s 超时 + 异常兜底 task | 任何一层失效都不会击穿到误吞 |
| 复用模型 | 分类与直答都走 Director 模型（MeteredChatModel 包装） | 成本记账、TPM 限流、演示 2M 额度、BYOK 解析与规划路径**完全一致**，零旁路 |
| 前端适配 | 复用 `chunk`+`complete` 事件 | 直答不发 `plan` 事件就不会出现任务进度卡，前端零改动；断线重放/持久化走同一事件通道 |
| 续跑豁免 | HITL 审阅后的 resume（resumePlan/initialTaskResults）跳过分类 | 续跑的 requirement 是原始需求，必然是 task，省一次调用 |

**延迟账**：分类均值 ~1.4s（p95 受 GLM 服务端波动 3~7s，线上 3s 超时兜底为 task）。闲聊路径总
TTFT = 分类 + 直答首 token，仍比原路径（规划 LLM + 多 Agent 数分钟）快一个量级；task 路径多付
一次分类调用（输入 ~600 token 估算，输出 ~8 token）。

## 3. 评测方法

- **黄金集** `eval/intent/golden-set.json`：77 例 × 12 类别。来源=人工构造 + **线上 Postgres
  `executions` 表真实语料**（含触发本次修复的「你能做什么」原句）。类别覆盖：寒暄/致谢/能力询问/
  附和/通用闲聊、各领域真实设计需求、**依赖平台知识库的提问**（必须 task，否则模型会编造本游戏数据）、
  **带历史的模糊延续**（任务语境的「继续」vs 闲聊语境的「继续」）、双向对抗样例
  （「你好，帮我设计签到系统」→task；「你会做数值策划吗」→chat）。
- **指标口径**：
  - `task→chat`（误吞）＝**危险指标，0 容忍**；
  - `chat→task`（漏判）＝安全指标，允许存在，逐例分析；
  - 延迟 p50/p95、LLM 调用次数、输出 token/例（输入 token 因网关不回传而缺失，见问题 #4）。
- **标注口径先于 prompt**：「帮我想 3 个游戏名」算 chat 是产品决策（轻量点子 vs 正式方案），
  先在评测集定标再改 prompt，避免 prompt 迁就模型输出、评测失去独立性。
- **运行**：`npx tsx --env-file=.env eval/intent/run-eval.ts --tag <轮次>`；报告 JSON 落盘
  `reports/`，带 prompt sha256 前 12 位（hash 可追溯，防止"改了 prompt 忘了测哪版"）。

## 4. 迭代记录

| 轮次 | prompt sha256 | 总体 | 误吞(危险) | 漏判 | 延迟 mean/p95 | LLM 调用 |
|---|---|---|---|---|---|---|
| v1 基线 | `3e707364328d` | 94.8%（73/77） | **0** | 4 | 1412 / 3286ms | 83 |
| v2 规则化 | `6b9b8d38018b` | 98.7%（76/77） | **0** | 1 | 1662 / 4036ms | 77 |
| v3 定稿 | `6e601ca0a845` | **100%（77/77）** | **0** | **0** | 1379 / 3119ms | 79 |
| v3 复测（稳定性） | 同上 | **100%（77/77）** | 0 | 0 | 1982 / 6592ms | 77 |

### v1 → v2：错例分析与修法（4 例全为漏判）

| 错例 | 判成 | 根因 | v2 修法 |
|---|---|---|---|
| 「游戏数值策划中，什么是期望值」（真实语料） | task | 领域词"游戏数值策划"触发了"专业内容→task"倾向 | 新增规则：通用概念/方法论问答**即使带专业领域词**，只要不涉及本游戏具体数据/文档/配置 → chat |
| 「帮我想 3 个赛博朋克风格的游戏名」 | task | v1 规则"帮我+策划内容→task"过强 | 新增规则：轻量头脑风暴与一句话点子 → chat；要求方案/文档/表格 → task |
| 「继续」（历史是概念解释） | task | v1 规则"继续→task"不看历史 | 新增"模糊延续词必须结合历史"规则：最近一轮是任务产出→task；闲聊/概念解释→chat；无历史→task |
| 「你会写剧情吗」 | task | "写剧情"字面命中产出动词 | 新增句式区分：**疑问句「你会/能不能+能力」= chat；祈使句「帮我+内容」= task** |

### v2 → v3：最后一例

- 「你能做什么设计」→ task。能力询问后接领域词（"设计"）仍被带偏，且该例伴随一次 30s 评测超时
  ——模型在这个真边界样例上"想太久"。v3 修法：给一组**对照示例**直接写进 prompt
  （「你能做什么设计/你能做什么类型的表格 → chat；帮我做一个签到系统的设计 → task」）。复测 100%。

### 迭代方法论小结

1. 每轮只改 prompt、不动代码，用 prompt hash 绑定报告；
2. 错例归因为**模式**而非孤例，修法写成通用规则 + 对照示例（示例比抽象规则对 LLM 更有效）；
3. 每轮盯危险指标（误吞=0）优先于总体准确率。

## 5. 过程中遇到的问题（实录）

1. **"已有意图识别"是个错觉**：接手时以为系统有意图识别（FAQ 快路径），排查发现它只在 query 模式、
   且工具已退役处于停用态。**修 bug 前先确认机制是否真的存在**。
2. **GLM 偶发不输出 JSON**（v1 全量中 2/77 例）：prompt 已强约束，模型仍输出自然语言，触发
   `generateStructured` 重试（+1 次调用、p95 拉高）。重试与降级兜底有效，v3 在 prompt 中追加
   "禁止输出任何解释或思考文字"后未再出现。
3. **网关不回传 input usage**：`usage_metadata.input_tokens` 恒为 0，输出 token 正常 → 评测的
   "输入 token/例"缺失，只能用字符数估算（~600 token）。改进方向：请求侧按 `chars/4` 估算，或网关
   开启 usage 回传。
4. **边界样例引发模型长时间思考**：v2 全量中出现一次 30s（评测上限）超时，正是那个最终错例——
   模型在真歧义上犹豫。**线上 3s 超时兜底不只是保护，而是产品行为的一部分**：难例自动回落为 task。
5. **评测并发与限速**：77 例并发 4 直连真实模型，压力可控（全程 ~2 分钟）；`--limit` 支持冒烟，
   先 `--limit 4` 验证脚本再全量。
6. **token 统计代理的零侵入设计**：不想为评测改 `generateStructured`（它丢弃 usage），改为在
   评测脚本里包一层 `ChatModelPort` 代理计数——生产代码零改动。
7. **评分双跑**：LLM 分类有非确定性（temperature 走服务端默认），v3 定稿后**复测一轮**确认 100%
   不是抽签；两轮指标一致才定稿。

## 6. 遗留风险与下一步

- **评测集规模 77 例偏小**，且 prompt 迭代已见过全部错例——存在过拟合风险。缓解：标注口径独立
  维护、错例修法写成通用规则而非枚举原句；**下一步**：从线上直答流量中周度抽样补充新例（目标 200+），
  并保留一批"holdout"用例只在定稿时跑。
- **线上监控未闭环**：已埋 span `intent.chat_hit`（观测台可查直答率），还需补充误吞信号——
  直答后用户立即追问任务（如 30s 内发出真实需求）视为疑似误吞，触发告警。
- **shadow 模式**：先"只分类不短路"跑一周，用线上真实分布验证误吞率再放开，适合用户量上来之后。
- **蒸馏路径**：若分类量级涨到日均万次以上，用已积累的分类日志微调小模型（0.5B 级）替换主模型分类，
  延迟可压到 200ms 内。

## 7. 面试问答预演

**Q1 为什么用 LLM 分类，不用规则/关键词？**
原系统 matchSkill 就是关键词打分，正是它把"你能做什么"误吞进工作流——关键词法无法处理中文语义
边界（「你会写剧情吗」vs「帮我写一段剧情」只差两个字的句式）。v1→v3 的 4 个错例全部是语义问题，
规则枚举追不完；LLM 二分类一次到位，且 fail-safe 兜底后风险可控。

**Q2 为什么不训练小模型/用嵌入相似度？**
数据与成本不匹配：标注数据只有 77 例，远不到训练/蒸馏门槛；嵌入分类在短文本意图上边界模糊且要维护
向量服务。而平台本身有 LLM 基础设施，边际成本约 ~600 输入 token/次。路线图里留了蒸馏：分类日志
积累到万级后微调小模型替换。

**Q3 误判把真实任务吞了怎么办？（最关键的问题）**
三层防线 + 一个指标。防线：① prompt 明示"判 task 从不亏、判错 chat 会吃掉任务，拿不准判 task"；
② schema 宽容解析，非 `"chat"` 一律 task；③ 3s 超时与任何异常兜底 task。指标：评测把 task→chat
列为 0 容忍的危险指标单独统计（四轮全 0）。另外直答 prompt 本身会引导"如果你想做设计，请描述
具体需求"——即使偶发误入直答，对话仍能拉回主流程。

**Q4 延迟和成本？**
分类均值 1.4s（GLM 服务端波动 p95 3~7s，超时兜底），输出 ~8 token；task 路径为此多付一次调用，
闲聊路径节省整个多 Agent 流程（分钟级 → 秒级）。

**Q5 评测集怎么建、怎么防过拟合？**
77 例 12 类别：人工构造 + 线上 Postgres 真实语料（含触发 bug 的原句）；特意覆盖两个方向的对抗
样例和带历史的模糊延续。防过拟合：标注口径先于 prompt 定（产品决策），prompt 迭代只学"错例的
模式"写成通用规则；下一步线上周度抽样扩充到 200+ 并设 holdout。

**Q6 怎么灰度上线？**
一键开关 `INTENT_CHAT_FAST_PATH`（默认开，可秒级回退）；观测台 span 看直答率；误吞信号
（直答后立即发任务）告警是下一步。量级上来后先 shadow（只分类不短路）验证线上分布。

**Q7 这次修复学到了什么？**
三点：① "系统有意图识别"要先验证机制真的存在且启用（FAQ 路径是停用的摆设）；② 错误代价不对称时，
fail-safe 方向要写进 schema 和超时兜底里，不能只靠 prompt 自觉；③ prompt 工程也要有评测闭环——
hash 绑定报告、每轮盯危险指标、双跑验证稳定性，否则"改好了"只是感觉。
